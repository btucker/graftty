# WSL2 AWS validation, November 2, 2026

The local WSL2 installer passed on an EC2 Windows Server 2025 instance with
nested virtualization. Graftty created a terminal through its patched zmx,
retained the shell across a host-service restart, and used more than half the
machine's RAM. This validates the Linux runtime path on WSL2. Windows 11
sign-in and screen-lock behavior remain unverified with a running WSL2 host.

[AWS documents WSL2 support on nested-enabled instances](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/install-wsl-on-ec2-windows-instance.html).
The installed AWS CLI 2.33.6 did not recognize the new CPU option. A temporary
Boto3 1.43.123 installation supplied the launch request and verified the result.
No global Python installation changed.

The instance had an encrypted 80 GiB gp3 root disk, no SSH key pair, and no
inbound security-group rules. Outbound TCP ports 80 and 443 supported downloads
and Systems Manager. Its dedicated IAM role allowed SSM agent channels and
instance registration only. No Graftty account credentials or paired endpoint
keys were copied to the guest.

## Preparation and artifact checks

The image's built-in `wsl --install --no-distribution --web-download` returned
exit 1 without installing WSL. Explicit Windows optional-feature enablement,
Microsoft's signed WSL MSI, and a reboot succeeded.

The following artifacts passed SHA-256 verification before use:

| Artifact | SHA-256 |

| `wsl.3.0.3.0.x64.msi` | `ae977286974255bd26bf925f00f40f5692c6b2084155cbc0563c09aea091f211` |
| `ubuntu-24.04.5-wsl-amd64.wsl` | `bb415d824822c4b878125729af451a5d18fb13d1cf5cbed9a7393ad64ac6039e` |
| `graftty-linux-0.8.0-alpha.21-x86_64.tar.gz` | `2f83187b36743db117df55ae57ab01d98569484f003c577ab3fda8c0fa9ce8c7` |

SSM ran privileged machine preparation. A separate, non-administrator Windows
account owned the distribution and ran the Graftty installer through a limited
scheduled task. That test account needed an explicit batch-logon right.
Its password was generated and consumed on the guest, without returning it
through SSM. The Linux development account was `graftty`, UID 1000.

Before importing Ubuntu, `Update-GrafttyWSLMemory` set a 12 GB ceiling in the
test user's `.wslconfig`. No processor override was set. Linux preparation
enabled systemd, configured the non-root default user, installed Git, and
enabled user-manager lingering. The test distribution then restarted before
installation. A foreground `wsl.exe ... sleep infinity` process kept the
utility VM alive during each test task.

## Results

`Install-GrafttyWSL.ps1` installed the verified Linux archive without SSH.
It reported `localReady: true`, `remoteReady: false`, and version
`0.8.0-alpha.21`. The systemd user service became active.

The installer reported these effective resources:

```json
{
  "logicalCPUs": 4,
  "allowedCPUs": 4,
  "memoryBytes": 12545773568,
  "availableMemoryBytes": 12168396800,
  "swapBytes": 3221225472,
  "cgroupMemoryLimitBytes": null,
  "cgroupCPUQuota": null
}
```

Windows reported 15.71 GiB of physical memory. The guest exposed 11.68 GiB
with the explicit 12 GB ceiling. All four CPUs were available through both
`os.cpu_count()` and process affinity. These are capacity checks, not CPU
throughput measurements.

The runtime smoke test passed these checks:

1. Register a Git repository under `/home/graftty/projects` and create a pane
   with `graftty pane add`.
2. Send shell input and wait for the executed output `GRAFTTY_BEFORE=survives`.
3. Record the host's zmx session list, then run
   `systemctl --user restart graftty-host.service` with `KillMode=process`.
4. Verify the same zmx session list and wait for `GRAFTTY_PERSIST=survives`
   from the original shell variable after restart.
5. Verify the SSH listener binds to `127.0.0.1:8801` and the disabled HTTP
   pairing listener is absent.
6. Allocate 9 GiB with Python `mmap`, touch every 4 KiB page, and verify
   `/proc/self/status` reports at least that much resident memory. Release the
   mapping after measurement.

The allocation reported `9,676,374,016` resident bytes, about 9.01 GiB. It
demonstrates memory growth beyond the usual half-RAM ceiling on this host.
It does not establish an optimal memory budget for builds or agent workloads.

The final limited-user task exited 0 and emitted:

```text
RESOURCE_LIMITS_OK
GRAFTTY_BEFORE=survives
GRAFTTY_PERSIST=survives
LOOPBACK_LISTENERS_OK
RESIDENT_MEMORY_BYTES=9676374016
NINE_GIB_MEMORY_ALLOCATION_OK
WSL2_GRAFTTY_ZMX_SMOKE_OK
```

An initial smoke run passed installation and session persistence but failed
an incorrect assertion requiring an HTTP pairing listener. The corrected run
required the loopback SSH listener and verified HTTP pairing remained disabled.
No production code changed for this correction.

## Coverage limits

This run did not exercise Windows 11 screen lock, interactive sign-in startup,
logout, sleep, or reboot recovery. The test's batch task supplied its own WSL
keeper and did not enable the production sign-in startup task.

It did not test cloud enrollment, Linux ICE/DataChannel support, TURN relay,
endpoint confirmation, or attachment from the parent Mac. Those connection
pieces remain required before `remoteReady` can become true.

## Cleanup

The instance reached `terminated`, and its root volume was deleted. The test
security group, IAM instance profile, inline policy, and role were deleted.
A final query found no active instances, volumes, or security groups with the
run's ownership tag. Existing VPCs, subnets, and IAM roles were left in place.

The instance ran from 14:20:20 UTC until termination was verified at
14:42:16 UTC, about 22 minutes. At the queried Windows rate of $0.39568 per
hour, compute cost was approximately $0.15, plus temporary disk and public IP
charges. This is a usage estimate, not a billing statement. A 90-minute
termination fallback was registered but manual cleanup completed first.
